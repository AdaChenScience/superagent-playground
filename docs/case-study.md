## 当前成果：从“有资料”到“准备试讲”

第一轮试刊交付完整，但用户仍觉得难懂。第二轮沿用原任务和 PR，让执行 Agent 安排写作与独立核查，交付零基础导读、口播稿与事实核查表。下文的“四个子 Agent、两次验收”专指第一轮试刊，不能直接当作第二轮计数。

第二轮有写作和独立核查的有效产出，也有未产出即停止的备用核查会话。具体会话及修订见[制作记录](video-001/fact-check.md)。Codex 成功投递一次验收反馈，随后还做了一轮本地最终修订；不能把最终稿全部归功于 Super-agent 自行发现问题。

最终稿围绕三个问题展开：为何延长文本、怎样检查训练能继续、为何这不等于长文能力已证明。把常规预测误差评测与专门能力测试分开，是最重要的事实修正。当前口播约 1,280 个汉字，按语速粗估 5–6 分钟；尚未录制、计时或通过真实初学者理解测试。“可以开始试讲”是当前验收结论，不是“教学效果已证明”。

## 问题与交付目标（第一轮试刊）

视频作者没有预训练团队背景，无法持续阅读 Marin 仓库中的大量讨论。需要在有限时间里知道：哪些进展值得讲、为什么重要、证据到哪一步、哪些结论暂时不能讲。

因此本轮的交付不是完整翻译仓库，而是三个排序选题和一个推荐选题的教学材料。原始数字和技术细节保留在证据附录，用户不必先看完工程日志。

观察窗口为 2026-10-19 05:30 至 2026-11-02 05:30 UTC。窗口内优先跟踪 535B-A23B 主训练，必要时引用旧记录解释背景。没有直接读取训练平台曲线或内部事故页。

## 设计选择

| 选择 | 原因 | 本轮证据或限制 |
| --- | --- | --- |
| GitHub Issue 作为任务入口，成果通过 PR 审阅 | 请求、反馈与修改放在同一可追溯位置 | 沿用 Issue #3、执行会话及 PR #4 |
| 两个研究子 Agent 分别查训练主线和评测 | 两条线可并行，避免只盯着原来的长上下文问题 | 实际创建两个独立会话；不是完整扫描全仓库 |
| 核查者自己读取原始评论与 PR | 研究摘要可能丢失条件，核查不能只复述摘要 | 找到次数、归因范围与评测类型的错误或歧义 |
| 教学改写后再使用 Humanizer | 语句自然不代表初学者能理解 | 仍需两次验收纠偏，说明提示词没有自动保证质量 |
| 主执行 Agent 统一整合文件 | 子 Agent 使用各自临时产物，减少互相覆盖 | 统一提交五份交付文件 |
| 把作者报告、测试、合并、主训练采用分开 | 防止把工程进度说成能力提升 | 每个关键结论保留来源和验证范围 |

## 真实执行链路

1. Codex 按用户授权，在原 Issue 追加试刊任务，明确范围、交付与权限。
2. Super-agent 将新消息关联到原任务，执行 Agent 收到要求。
3. 初始任务已要求研究、核查和写作分工；执行 Agent 将研究拆成两条线，并实际调用 DSH 的 `subagent` 工具，委派两个研究会话、一个核查会话、一个写作会话。分工要求来自 Codex 编写的任务，具体拆分与调用由执行 Agent 完成。
4. 研究产物用于核查和写作；核查修正通过消息继续交给写作和主执行 Agent。并非所有阶段严格串行等待。
5. 写作 Agent 读取本机 Humanizer-zh 全文，用于保留含义的表达编辑。它没有通过 DSH `skill` 条目加载该技能。
6. Codex 两次验收反馈继续进入原任务；主执行 Agent 修改、核对并更新同一 PR。

四个会话的 ID 和具体职责见[运行记录](pilot-001/run-record.md)。这份记录是模型整理的审计说明，原始工具调用存在本地 DSH 会话日志中；公开文档不等于公开了完整原始日志。

## 三个值得保留的修正案例

### 把“没评测”说准确

草稿容易将“缺少 32K 以上专门的长上下文能力基准”压缩成“没有长上下文评测”。核查发现，这会混淆 loss 评测和专门的能力测试。

最终保留区别：训练或留出文本上的预测误差仍能计算；它不能直接证明模型能完成复杂的长文本任务。[证据及修正](pilot-001/evidence.md)

### 不把局部复现推广为所有异常的原因

梯度尖峰调查中，不同训练步的复现条件不同。某一次异常可以追到具体输入和计算，不代表其他异常也已查明原因。

最终写明复现范围，并区分“加入梯度裁剪”“小规模测试触发裁剪”和“主训练观察期间尚未触发”。没有把部署动作当成已证明解决问题。

### 润色之后仍然难读

第一版简报仍堆积 CP/EP、dropless、Paloma macro 等词。即便删掉套话，读者仍不知道这些变化为什么重要。

第一次验收要求减少缩写、纠正“单机”与“单机架”的区别；第二次纠正 token、训练存档等定义，并要求把配置细节移到可选附录。最终正文围绕“为何延长文本、如何控制风险、为何能力仍待证明”展开。

这说明 Humanizer 解决表达问题；教学结构、事实核查与读者验收仍需要单独设计。

## 结果如何评估

已完成：三个排序选题、一份教学材料、证据表、跟踪快照和运行记录；真实委派四个子 Agent；两次追加验收进入原任务并更新原 PR。

本轮计数为 **2 次 Codex 验收指导、0 次用户追加决策**。派发初始要求不计入追加指导，Agent 内部讨论也不计入。这个指标不代表没有监督成本。

没有测量阅读时间节省、API 成本、覆盖率或事实准确率；没有与单 Agent 对照。因此不能宣称更快、更便宜、无遗漏或完全自动化。研究记录与核查相互印证也不能代替 GPU 实验或第三方复现。

## 我的贡献与工具贡献

用户提出真实视频需求，决定受众与验收目标；Codex 协助配置、派发、验收与展示整理；Super-agent 和 DSH 提供任务管理与执行能力，模型生成内容。不是用户手工写了所有材料，也不是用户开发了底层框架。

这是一份可以讨论需求转化、Agent 分工、证据约束、反馈续接和验收边界的实践案例。下一步只有在需要制作新一期视频时，才值得验证增量更新；当前不继续堆叠演示功能。
