# 教学稿：Marin 开始练习读更长的文本：切换成功，离能力证明还有多远？

## 开场（约 30 秒）

2026 年 11 月 2 日凌晨（UTC），Marin 535B-A23B 这条由许多专家分工处理的模型（MoE）主线把训练上下文从 16K 提到 65K。切换发生在第 372,000 步，离总步数 390,251 只剩 4.7%。这是一次带六项上线检查（放行条件）的工程切换，不是能力发布。

## 问题：为什么把 65K 放在最后

训练语言模型，就是让模型不断猜下一个 token。token 是文本的最小单位，可以粗略理解成一个词或半个词。上下文是模型一次能看到的 token 数。K 在这里指 token 数：4K 约 4 千，16K 约 1.6 万，65K 约 6.5 万，262K 约 26 万。上下文越长，模型能利用的前文越多；代价是注意力（模型在序列里决定看哪些位置）要处理更多两两关系，显存和跨卡通信都会涨。序列切成多段放到多张卡上时，卡与卡之间要交换中间结果，切得越细，通信越多；这会影响后面的 CP 取舍。

loss 是模型猜下一个 token 的错误程度，越低说明在这批数据上拟合得越好；它不等于能力更强。

所以常见做法是先短后长：大部分步数用短上下文跑完，最后一段再拉长。短上下文便宜，能多跑；长上下文只在尾段跑，让模型适应更长的输入。这条主线在 10-14 已经从 4K 切到 16K，那是窗口外的背景；现在把 65K 放在最后 4.7%，262K 阶段排在后面。

训练中途会存 checkpoint，也就是权重快照。这次切换就是从第 372,000 步的永久（长期保留）checkpoint 长出一个新子 run（从该快照接着跑的新训练进程）。checkpoint 的作用是出问题时能回到这里，不用从头再来。保存成功不等于能恢复；两次单机架排练只验证了保存，没有验证恢复，所以切换时还要盯恢复这一步。

这里用一个填空句做教学比喻（类比），不是真实实验：

“今天下雨，出门要带___。”

如果前面再加一句“昨天预报就说今天有雨，早上天一直很阴”，空格处填“伞”的可能性会更高。前文越多，答案越可预测。模型的上下文变长，作用类似：能参考的前文更多。

但在真实评测里，改变打包长度本身也可能让分数移动。打包是把多条短文本拼进一个定长序列，减少补齐长度（padding）的浪费；打包长度会改变评测时看到的序列边界，所以切换后第一次评测即使分数动了，也要先排除口径变化。10-22 有独立观察者在几乎相同的权重上测到，16K 打包的 Paloma 评测集的总分（各子集分数的平均）比 4K 低约 0.031；这是单次权重快照、单次测量，不是 Marin 官方评测，也没有复现。它说明“上下文变长”和“分数变高”不能直接画等号。

## 团队做了什么

决策在 10-31 到 11-01 之间定下：在第 372,000 步切换。CP 是上下文并行，把一条长序列切到多张卡上算；EP 是专家并行，把 MoE 的专家分到不同卡上。配置是 CP1×EP64（CP1 指长文本不切，专家铺到 64 路）。

capacity factor 是每个专家允许接收的 token 容量倍数，设小了会丢 token，设大了浪费显存，这次取 1.5；qk_mult 是注意力打分的缩放系数，换上下文长度时要跟着调，这次取 1.66。

为什么不是 CP4×EP16（长文本切成 4 段、专家铺到 16 路）？单机架 500 步对照看步时、drop 和显存。drop 是 MoE 路由（给每个 token 选专家）丢掉的 token 比例，dropless 是尽量不丢 token 的路由方式。CP4 是 14.699 秒/步、drop 2.41e-3、127.6 GiB；CP1 是 15.397 秒/步、drop 9.80e-4、128.4 GiB。CP4 把一条序列分给 4 组卡，单卡压力更小、步时更快；但它 drop 更多，而且它的 dropless 评测在评测显存问题（#10709）修好前会让下一步训练失败。CP1 慢 4.7%，但 drop 少 2.5 倍，更稳，所以这次用 CP1，CP4 留给 262K。

上线前还做了两次单机架排练。第一次（C1）从第 360000 步跑 60 步，15.571 秒/步，drop 8.29e-4，做了三次 dropless 评测，没有 OOM（显存不足）；第二次（C2）从第 366000 步跑 100 步，15.518 秒/步，drop 1.00e-3，127.9 GiB，做了两次权重快照保存，最终 4.29 TB（存储容量单位）的第 366100 步权重快照完整。但权重快照恢复没有测。

部署发生在 11-02：合并请求（PR）#10820 在 02:55:41Z 合并，子训练 03:25Z 启动，03:28Z 从第 372000 步恢复，03:34Z 跑出第一步。04:03:06Z，六项上线检查在第 372,102 步全部通过，第一次尝试，没有重试。这些检查是上线前的一组放行条件，任何一项不过就不算通过；这次是检查通过，不是又一次 GPU（显卡）排练。尾段只剩 18,251 步，试错空间小，所以先排练、再切换、再看检查。

## 证据：六项上线检查各自防什么

| 检查项 | 结果 | 在防什么 |
|---|---|---|
| 交叉熵（CE）最大值 | 1.007 | 切换后 loss 没有突然爆高 |
| loss 差（子 run 减父 run） | −0.02009 | 新上下文没有让 loss 跳变 |
| 中位步时（一半的步快于它） | 16.05 秒 | 变慢在可接受范围 |
| drop 均值 | 4.058e-4（约 3.5e-4–4.1e-4） | 路由丢 token 没有升高 |
| 峰值 HBM（GPU 显存，单位 GiB） | 127.8 GiB | 显存没有顶到上限 |
| 持续梯度尖峰（梯度范数突然变大） | 没有 | 梯度没有持续失控 |

CE 是语言模型常用的 loss 形式，衡量模型给正确的下一个 token 分配的概率高不高；这里看的是它的最大值有没有异常。

父 run（旧配置的对照）是：14.38 秒/步、loss 0.9982、drop 1.396e-3、HBM 123.2 GiB。用 16.05 对 14.38 算，吞吐约少 10.4%；按表里的 tok/s（每秒处理的 token 数）算约少 11.0%。对外说“约少 10%”，不要用那个按 16.3 秒/步做的预估，它不是实测。

归因也要分清：六项上线检查由 Marin 作者方/代理报告，没有独立复核；10-22 的 0.031 是外部观察者的测量，不是官方评测。两者不能混着说。

## 不能夸大的结论

- 截点前没有 65K 评测结果。32K 以上没有长上下文能力基准，一套长上下文能力测试（RULER）的接入问题 #7638 在 10-24 被自动清理机器人关闭；65K 阶段只能靠 loss 判断，训练侧的 loss 仍会评，Paloma 这类留出未训练的 held-out 数据也算在内；但它不是能力基准。
- 评测按训练长度打包。切到 65K 后，Paloma 评测集的总分可能阶跃，eval_regressed（评测回归告警，相对父 run 2%）可能误报。这是测量风险，不是“已经回归”。
- 多长度评测的修法（#10711）已批准，但还没合并、与主分支有冲突，也还没有在 GPU 上排练；ClassicLarry 问过，保留最后一个不满打包块（partial chunk）会不会改变 4K/16K 数据，到截点没有实验。
- 评测显存问题的修法（#10709）也还没合并，仍在等评审：单机架 65K、CP4 时每 GPU 多约 7.4 GiB，余量约 5.8 GiB，下一步训练分配失败；11 个机架没测。
- 训练没有结束。最后确认的是第 372,102 步，预计 11-05T15:00Z 完成；首次 65K 评测在第 375,000 步（约 11-02T17:20Z），永久权重快照在第 378,000 步（约 11-03T07:00Z），都在截点之后；262K 还没开始。
- 上线检查只覆盖 103 步，也只有这一条训练的一次切换。它证明的是切换那一刻没有翻车，不是接下来 18,251 步都不会翻车；通过检查只说明“没有明显回归”，不说明长上下文能力；合并请求是工程动作，不是能力结果。
- Marin 承诺在训练结束后用 4K 重评所有权重快照；到截点没有公开记录，承诺条件是训练结束，所以现在还不能算逾期。

## 讲解顺序与时间（5–8 分钟）

1. 0:00–0:30 开场：一句话说清“最后 4.7% 换 65K，是工程选择”。
2. 0:30–2:00 问题与术语：token、上下文、checkpoint、loss；为什么先短后长；填空类比，加上打包口径的提醒。
3. 2:00–4:00 团队行动：时间线；CP1 与 CP4 的取舍；capacity factor 和 qk_mult；部署与上线检查。
4. 4:00–5:30 证据：六项上线检查逐条；父 run 对照；吞吐约少 10%；作者报告与独立观察的区别。
5. 5:30–6:30 不能夸大：没有 65K 评测结果；评测打包风险；多长度评测与评测显存问题的修法都还没合并；训练未结束。
6. 6:30–7:00 收尾：下一步看第 375,000 步首次评测、第 378,000 步永久权重快照、11-05 完成、262K。
